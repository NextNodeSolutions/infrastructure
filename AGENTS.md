# Rules for changing this repository

These are the rules for changing the workflows of this repository and the program behind them, for people and agents alike. The README says what a run does, [docs/architecture.md](docs/architecture.md) how the parts fit, [docs/deployment.md](docs/deployment.md) how a merge is deployed and [docs/nextnode-toml.md](docs/nextnode-toml.md) what a project writes. This file says what must stay true and why.

## What the project guarantees

A change that weakens one is wrong, even when it compiles.

1. **The same workflows serve every project.** A project repository holds no workflow file. What a project must express goes through its root `package.json` and, to be deployed, one `nextnode.toml` per deployable. Reason: a per-project copy drifts, and a fleet-wide fix must land in one place.
2. **The workflow file carries no logic.** It names when the workflow runs, what it may touch, which jobs exist, how they depend on each other, the actions it pins, and one line per job that calls the program. Every decision, from reading the manifest to choosing the command a check runs, is made by the program. Reason: the program is type-checked and linted on every pull request of this repository, by this very workflow. Shell written in YAML is checked by nothing until it runs inside every project.
3. **A job runs the program committed beside the workflow file it executes.** Each job fetches this repository at the commit GitHub reports for the workflow that defines the job, and runs the program from that checkout. Reason: a branch under test then runs the branch's program and `main` runs the program of `main`, with no reference to bump and no second copy to publish.
4. **A workflow runs only what the repository declares.** No `package.json` means nothing to check and a green run, and no `nextnode.toml` means nothing to deploy and a green run. A script that does not exist is not a check. A workspace package is checked only when the change can reach it. Reason: a check that cannot apply either fails for a wrong reason or hides behind an "optional" flag, and both teach people to ignore red.
5. **Selection follows the package graph.** Changed packages and their transitive dependents, through the package manager's own filter. A root file selects everything. Reason: path filters cannot see that a shared package feeds an app, and a workflow-level path filter leaves required checks pending forever.
6. **Discovery refuses before any job installs.** A manifest that cannot be read, a missing `packageManager`, a missing or too old `engines.node` fails the Discover job with an annotation on `package.json` naming the field. Reason: one message that says what to add beats five jobs failing the same way.
7. **A job that reads or runs the project holds nothing that writes.** Its token only reads, it cannot ask for an identity token, and no checkout keeps a credential. `Checks` is made of such jobs alone. No workflow file holds a `secrets.` reference: what a release needs comes from the vault and the registry, admitted by the run's identity. Reason: the jobs run the project's code, its dependencies and their lifecycle scripts. Whatever the job holds, that code holds too.
8. **A value the project controls never reaches a shell.** Package names, script names and the matrix travel as JSON that a decoder reads and as argument arrays that a child process receives. The one `run` line of a job names no project value. Reason: as command text, a package name would be shell code written by the project.
9. **Everything is pinned.** Actions by commit SHA with the release tag beside it, the runner image by version, the program's own Node by the exact version in `.node-version`, the program's dependencies by exact version and its lockfile, the project's Node by the major its manifest declares. Reason: a tag can move, a SHA cannot.
10. **Only the default branch deploys, through the standing pull request.** The jobs that hold something decide which pull request they serve from the event GitHub wrote, and refuse every other before they read anything of the project or ask for a credential. The vault admits the same run by the claims of its token and nothing else. Reason: any branch can open a pull request into the branch deployments run on, and that code is unreviewed.
11. **A job that holds something that writes runs nothing of the project.** It checks out nothing of it and installs nothing of it. It reads a declaration at the commit through the API, and takes what a build left as plain files to upload. The tools it starts get the variables the program names and a configuration the program wrote, and the run's identity reaches none of them. Reason: the Cloudflare token reaches the whole account and the run's identity opens the vault, so one project process beside them would hold every project.
12. **A file names no resource.** Every name comes from the repository and the package. A Worker carries the repository that deploys it and no other repository uploads over it, and a hostname is taken only when nothing holds it. Before writing, resource names are reserved atomically in the private state bucket for the immutable repository id and deployable. Claims are never replaced or expired automatically. Reason: every project deploys into one account with one token, so the program is the only thing between a `nextnode.toml` and another project's Worker, data or address.
13. **A deployment is decided against the last one that succeeded.** Per deployable, read from GitHub's deployment records and verified against a successful Release job of the ruleset-required Deploy workflow. The pipeline stores no release history of its own. Reason: a failed, cancelled or missing run then heals at the next one, and a re-run needs no cleanup.
14. **A release never goes backwards and never deletes.** A run whose commit is no longer the default branch tip refuses before it requests credentials, independently of deployment records. A database or a bucket whose binding left the file stays in the account. A version is published once. Reason: these are the three losses a re-run or a careless edit could cause, and none of them can be undone by the next run.
15. **Every run explains itself where it ran.** Each job's summary says what it decided or deployed and why, a deployment is recorded with its address, and a failure says its cause and the next action. Reason: nobody watching a deployment has this repository open.

## Architecture rules

- **A workflow file holds what only GitHub can read.** Triggers, permissions, concurrency, the jobs with their `needs`, `if` and matrix, the pinned actions with their inputs, and an `env` block that hands a matrix entry, an output or the job's token to the program as one variable. A `run` step is one line that names a command of the program. A second line, a pipe, a condition, a default or a variable set in shell is logic, and logic moves to the program. Reason: guarantee 2 is kept by the shape of the file, which a reviewer checks at a glance.
- **Permissions are granted per job, to the job that needs them.** A workflow grants reading at its top, and a job that records, writes or asks for an identity token says so itself. Reason: guarantees 7 and 11 are then read off the file, job by job.
- **The program runs from its checkout with Node, and has no build step.** Node strips the types as it loads the files, so only erasable syntax is allowed and import specifiers carry their `.ts` extension. Reason: a build output would be a second copy of the code that the type checker does not see.
- **The check commands have no dependency. The deploy commands install their own.** The program installs them itself after it left the project tree, from its own lockfile, with the pnpm its manifest pins and lifecycle scripts off. A dependency is imported where it is called, never at the top of a module. What every deploy job parses with is a dependency, and what only bundles, uploads or provisions is an optional one, so a job installs what it uses. Reason: an install inside the project tree would run under the project's `.npmrc`, and a top-level import would make the check commands need an install.
- **The program leaves the project tree before anything of the project runs.** Its checkout lands inside the workspace, because that is where GitHub lets a checkout land, and the program's first act moves it to the runner's scratch directory. Reason: the project's lint, format and test tools walk the tree they run in, and a platform file in that tree is a project file to them.
- **The program is in layers, and a dependency points inward.** The domain takes data and returns data: manifests, selections, plans, commands as argument arrays, outputs, the summary. It imports nothing outside itself. An adapter holds one kind of IO, such as files, child processes, git, pnpm or the GitHub channels, and may read the domain's types. A command wires adapters and domain for one job, and the entry point dispatches on the command name. The lint configuration enforces the direction, so a new import that crosses it is a design change, never a rule to relax. Reason: the domain is what a test runs without a runner, and the adapters are what a test replaces.
- **Discovery is the only job that reads the repository's shape**, with full history checked out. Every other job consumes its outputs. Reason: one place decides, so one job summary explains the decision.
- **A release takes discovery's outputs as a request.** It reads the declaration again at the commit through the API, and refuses when the commit derives another name than the one it was asked for. Reason: discovery ran the project's package manager, so its outputs are the project's word, and the job that holds credentials acts on the commit alone.
- **A build hands a release plain files.** The build stages them outside the project tree and the release refuses anything that is neither a file nor a directory. The release uploads the bundle the build made without bundling again. Reason: the code that serves is then the code the build produced, and nothing the build left can point the release elsewhere.
- **The run's identity stays in the program.** A token, a credential or the variables that ask GitHub for an identity token are read once and removed from the environment. A tool is started with the variables its adapter names. Reason: whoever holds the run's identity can ask for a token any service would admit.
- **Each outside system has one adapter, and the platform's accounts are named in one place in the domain.** None of those names is a secret. Reason: the vault admits by claims, so knowing an id opens nothing, and one home keeps a move of account to one edit.
- **The platform writes the configuration a tool runs on.** A project's file is decoded into a typed declaration with every unknown key refused, and the configuration is built from that declaration and the derived names. Reason: a key passed through untouched is a key a project can use to name another project's resource.
- **Discovery acquires pnpm after it has validated the manifest**, at the declared version, through the npm that Node ships. The check and build jobs take pnpm from the pinned action instead, because the dependency cache must find pnpm before Node is set up. Reason: the refusal of a bad `packageManager` must come from the program, with its annotation, not from a tool that read the field first.
- **The executor is chosen from what the repository contains**, in the order single package, workspace, workspace with `turbo.json`. Reason: a repository that adopts a task runner declares its task graph there, and the workflow should run through it rather than guess the graph.
- **The matrix is JSON produced by discovery and read with `fromJSON`**, with the check job guarded by an empty-matrix condition. Reason: an empty matrix is a workflow error, not a skipped job.
- **Statuses are named after the check and, in a workspace, the package.** The ruleset reads the run's conclusion, not a job name, so names can follow the project. Reason: names that vary per repository cannot be listed in a ruleset.
- **The known scripts live in one catalogue in the domain.** Adding a check is adding a script name and its label there. Reason: the matrix, the summary and the statuses all derive from it.
- **Outputs and workflow commands go through the GitHub adapter.** An output is one line, and the adapter refuses a value with a line break. An annotation or a log group escapes its text. Reason: both channels are line protocols that GitHub parses, and a project value with a newline would otherwise write a second output or a second command.

## Code rules

- Formatting, lint rules and compiler options come from the shared standards package. The three config files at the root extend its presets, and the lint config adds the layer restrictions. Fix a finding by redesign, never by disabling the rule.
- A comment states an invariant, an external constraint or a workaround with its reason, in one sentence. Everything else is said by names.
- A child process receives its arguments as an array and never a shell. A command is a value of the domain, built by a table keyed by executor, so the type checker lists every table a new executor must cover.
- Unknown input, which is a manifest, a `nextnode.toml`, a pnpm listing, a job variable, GitHub's event or the reply of an outside system, is decoded at its boundary into a typed value. The rest of the program takes the typed value.
- A refusal a project can fix names the file, the key and what to write, and is raised as the refusal type that becomes an annotation on that file. Any other failure is an error that names what refused and why.
- In the workflow file, a pinned action keeps its release tag in a trailing comment, and a value a job hands to the program goes through `env`, never into the `run` line.

## Checks

- `pnpm lint`, `pnpm format:check` and `pnpm type-check` pass. The repository's own pull requests run this very workflow, so the scripts its manifest declares and the catalogue knows run there too.
- The program runs locally against the canary checkouts before a push. Set the variables a job would have (`GITHUB_WORKSPACE`, `GITHUB_OUTPUT`, `GITHUB_STEP_SUMMARY`, `GITHUB_EVENT_NAME`, `GITHUB_BASE_REF`, `RUNNER_TEMP`), make the project the working directory and run the `discover`, `check` and `build` commands of the entry point. A workspace scenario is a commit on a scratch branch of the workspace canary: one app changed selects that app, the shared package changed selects it and its dependents, a root file changed selects everything, Markdown alone selects nothing.
- A change to the workflow or the program is tested on the canaries before it merges. Point the ruleset's workflow entry at the branch, open a pull request on each canary, cite the runs in this repository's pull request, then point the ruleset back. Two canaries exist because the workflow has two shapes: `canary` is a single package, `canary-workspace` a pnpm workspace whose shared package feeds an app.
- A change to the deploy workflows or commands is proven on both canaries by real merges, since the repository has no test runner: the single-package canary deploys its static Worker, the workspace canary deploys a Worker with a database and a bucket that a real request writes and reads, and a change to one package releases only what it reaches.
- The probes of [docs/deployment.md](docs/deployment.md#probes) run again after a change to a job that holds something, to the event decoding or to the vault's admission. Each is an attack that must fail.
- Reviewing a change means walking the trust boundary tables of the architecture and deployment pages again: what new thing does the job hold, and which new value from the project reaches a process, a file or a channel.

## Commits

One intention per commit, as a Conventional Commit: `ci(scope): what changed` for the workflow and the program, `chore: what changed` for tooling, `docs: what changed` for documentation alone. Documentation that a change makes wrong is updated in the same commit. Pull requests are squash-merged, so the title reads as one commit.

## Documentation

The README, the pages under `docs/` and this file describe intent and rules, never the current inventory: no action versions, no list of repositories, no copy of a value the workflow or the program sets. Script names, `package.json` fields, `nextnode.toml` keys, the name of the branch deployments run on and the command names of the program stay, because they are the contract a project and the workflow write against.

**The docs describe the intended behavior.** That covers `docs/`, the README and this file. When a change makes them wrong, do not just rewrite them to match. First check that the change is expected: the task asks for it, or the user confirms it.

- If it is expected, update the docs in the same commit as the change.
- If it is not, the docs win. Bring the code back in line with them, or stop and ask.

## Working against real systems

The organization rulesets and the canary repositories are shared state. Pointing a ruleset at a branch changes what every listed repository runs. Do it for a test, say so, and point it back when the test ends. A pull request opened on a canary for a test is closed afterwards.

A deployment is real. A merge on a canary changes what its addresses serve, creates resources in the platform's Cloudflare account and can publish a version that the registry keeps forever. The vault's admission of the `Deploy` workflow names the workflow file's ref: adding a branch under test to it lets that branch's program hold the platform's credentials, so add it for the test, say so, and remove it when the test ends. Deployments run in CI only. Local credentials are for reading, and nothing in the account, the vault or the registry is deleted without the owner's word.

## Extending

- **A new check**: add the script name and its label to the catalogue in the domain. The status, the summary and the matrix follow.
- **A new executor**: add it to the executor union and to its detection. The type checker then names the command tables that need an arm. The arm receives the package and the script as values and must honor the project's task graph.
- **A new root file that invalidates everything**: add it to the root file list in the domain, with the reason every package depends on it.
- **A new job**: a job in the workflow file with its pinned setup steps and one `run` line naming a new command. The command is a module beside the existing ones, wired in the entry point's dispatch table. Decide first which side of guarantees 7 and 11 it stands on.
- **A new key of `nextnode.toml`**: add it to the decoder and the typed declaration, then to the configuration the release writes. A key that would name a Worker, an account or a resource is not added: derive the name.
- **A new kind of resource a Worker binds**: add its binding to the declaration, its name to the resource plan and its creation to the provisioning program, kept when its binding leaves the file.
- **A new kind of deployable**: add it to the declaration union. The type checker then names the build and the release that need an arm.
- **A new environment**: production keeps the bare name of the deployable. Another environment takes its own name as a suffix, for the Worker, the GitHub environment and the stack, so adding it renames nothing that serves.
- **A new outside system**: one adapter that decodes its replies, its account named in the domain beside the others, and a row in the credential table of the deployment page.
